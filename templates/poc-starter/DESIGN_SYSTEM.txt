## Rules for AI coding tools

1. Always use our registry first. For the 10 components listed above,
   always pull from our registry URL, never from the public shadcn registry
   (`https://ui.shadcn.com`) and never hand-roll HTML.

2. Fall back to the public shadcn registry for any component NOT in our
   list (e.g. Accordion, Slider, Calendar). The public components inherit
   our tokens automatically via CSS variables — no extra work needed.
   ```
   npx shadcn add accordion   # public registry — fine for unlisted components
   ```

3. Never hand-roll form elements. Always use `<Input>`, `<Button>`,
   `<Select>`, `<Form>` etc. from `@/components/ui/*`. Raw `<input>`,
   `<button>`, or `<select>` tags are not acceptable in POC code.

4. Never hardcode hex values or Tailwind color literals like
   `bg-orange-500`, `text-[#f25011]`, or `style={{ color: '#f25011' }}`.
   Use CSS variable tokens exclusively (see table below).

5. Dark mode is handled automatically by a `.dark` class on `<html>`.
   Never write manual dark-mode logic against these tokens.

6. Import path is always `@/components/ui/<name>` after running the
   registry install command.

## Token reference

All values are CSS custom properties set in `app/globals.css`.

### Brand

| Token               | CSS Variable          | Light value | Dark value  | Use for                        |
|---------------------|-----------------------|-------------|-------------|--------------------------------|
| Primary             | `--primary`           | `#f25011`   | `#f25011`   | Primary buttons, links, rings  |
| Primary hover       | `--primary-hover`     | `#e0470f`   | `#e0470f`   | Button hover state             |
| Primary active      | `--primary-active`    | `#cf400d`   | `#cf400d`   | Button pressed state           |
| Primary foreground  | `--primary-foreground`| `#ffffff`   | `#ffffff`   | Text/icons on brand bg         |

## Usage conventions

- Import path: `import { Button } from "@/components/ui/button"` (always
  `@/components/ui/*`, never a deep relative path)
- Variant naming: `variant="default"` is always the primary brand action
- Sizes: `size="sm"` | `"default"` | `"lg"` | `"icon"` (Button)
- Form pattern: always pair `<Input>` with `<FormLabel>` + `<FormControl>`
  inside a `<FormItem>` — never a raw label/input pair
- Dark mode: add `dark` class to `<html>` or use
  `next-themes` ThemeProvider — never write per-component dark: overrides
  for the variables listed above

## Code examples

### 1. Primary action button

```
// GOOD — uses registry component, brand token via variant
import { Button } from "@/components/ui/button"
<Button>Save changes</Button>

// BAD — raw HTML, hardcoded brand color
<button style={{ backgroundColor: "#f25011", color: "#fff" }}>
  Save changes
</button>

// BAD — Tailwind color literal instead of token
<button className="bg-orange-500 text-white rounded-md px-4 py-2">
  Save changes
</button>
```

### 2. Form field

```
// GOOD — Form + Input from registry, accessible labels wired automatically
import { Form, FormField, FormItem, FormLabel, FormControl, FormMessage } from "@/components/ui/form"
import { Input } from "@/components/ui/input"

<FormField
  control={form.control}
  name="email"
  render={({ field }) => (
    <FormItem>
      <FormLabel>Email</FormLabel>
      <FormControl>
        <Input placeholder="you@example.com" {...field} />
      </FormControl>
      <FormMessage />
    </FormItem>
  )}
/>

// BAD — hand-rolled, no accessible association, wrong tokens
<div>
  <label className="text-sm font-medium">Email</label>
  <input
    className="border rounded p-2 w-full mt-1"
    placeholder="you@example.com"
  />
</div>
```

### 3. Status badge

```
// GOOD — semantic variant, token-driven color
import { Badge } from "@/components/ui/badge"
<Badge variant="destructive">Failed</Badge>
<Badge variant="success">Active</Badge>
<Badge variant="warning">Pending</Badge>

// BAD — hardcoded color, bypasses token system
<span className="bg-red-500 text-white text-xs px-2 py-0.5 rounded-full">
  Failed
</span>
```

### 4. Card layout

```
// GOOD — structured slots, tokens applied by the component
import { Card, CardHeader, CardTitle, CardDescription, CardContent } from "@/components/ui/card"

<Card>
  <CardHeader>
    <CardTitle>Project overview</CardTitle>
    <CardDescription>Current sprint status</CardDescription>
  </CardHeader>
  <CardContent>
    <p>Content here.</p>
  </CardContent>
</Card>

// BAD — manual shadow, hardcoded border, no token usage
<div className="rounded-lg border border-zinc-200 bg-white shadow p-6">
  <h3 className="text-lg font-semibold">Project overview</h3>
  <p className="text-zinc-500 text-sm">Current sprint status</p>
</div>
```

### 5. Per-client re-theming

```
/* GOOD — swap only the brand tokens in globals.css for a new client */
:root {
  --color-brand: #0066cc;        /* client brand color */
  --color-brand-hover: #0052a3;
  --color-brand-active: #003d7a;
  /* all other tokens unchanged — every component updates automatically */
}

/* BAD — hardcoded color in a component file */
.btn-primary {
  background-color: #f25011;     /* now this breaks on every client re-theme */
}
```

### 6. Adding a new component

```
# GOOD — pull from our registry first
npx shadcn add https://FissionHQ.github.io/ui-design-system/r/select.json

# For anything not in our 10, fall back to public shadcn — tokens still apply
npx shadcn add accordion

# BAD — never do this for our 10 components (gets unthemed public version)
npx shadcn add button
```

## Per-client re-theming

Only these variables need to change for a full brand swap:

```
--color-brand
--color-brand-hover
--color-brand-active
--color-on-brand
--color-sidebar   (optional — only if client has a distinct sidebar color)
```

All other variables (zinc scale, state colors, layout tokens) stay the same
unless the client has specific requirements. Change them in `globals.css`
only — never touch component files.
